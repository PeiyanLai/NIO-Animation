# 交付流程：对话框发 HTML → 生成飞书文档 → 动画平铺在文档里

> 面向公司内部 agent（已打通飞书文档）。团队成员用本 skill 生成动画后，
> **每一次都要走完这两步**，不要只丢一个链接就结束。

## 先回答那个最关键的问题

**「能不能让团队成员在飞书文档里直接看到动画，不用点链接跳到另一个网页？」——能，但只能靠 GIF。**

飞书文档**没有能运行 HTML 的块**（不支持任意 iframe/脚本），所以交互 HTML 无法在文档里跑起来。
文档里唯一能「自己动起来」的是 **GIF 图片块——插进去就自动循环播放，零点击**。

所以正文里平铺的是 GIF，HTML 以链接和附件的形式跟在旁边，给需要暂停逐帧、切章节细看的人用。
这不是降级方案，是飞书文档的能力边界；把它说清楚比让人反复试更省时间。

## 飞书文档各种块的能力边界

| 块类型 | 打开文档时 | 用途 |
|---|---|---|
| **图片块（GIF）** | ✅ **自动循环播放，零点击** | **正文里的动画展示，主力** |
| 视频/文件块（MP4） | ⚠️ 卡片内点击播放 | 成片、长内容、要高清时 |
| **文件块（HTML）** | ⚠️ 下载后本地打开 | **可交互完整版，必放** |
| 超链接文本 | ❌ 大概率 403，见下 | 别单独依赖 |
| 内嵌网页块 | ❌ 不能跑我们的 HTML | — |

### HTML 千万不要只插链接（实测踩过）

agent 把 HTML 传上聊天网关后拿到的是一条**签名 URL**（`…?sign=xxx&t=1786958504`）。
这种链接的签名绑在**签发时的会话/时效**上，agent 自己的对话框里点得开，
**别人从飞书文档里点开就是 403「您未获授权」**。团队成员会以为动画坏了。

正确做法：**把 HTML 文件本体作为飞书 file 块上传**（`parent_type=docx_file`），
权限跟着文档走，完全不经过外部 CDN。点击是下载，下载后双击用浏览器打开——
本 skill 产出的 HTML 是全内联单文件，**离线也能完整播放**，这点要在文档里写一句告诉大家。

链接要留就留在文件块**旁边**，并标注「仅签发者可见，失效请下载附件」；
想让链接真能点开是 infra 的事——去问那个网关能不能签发组织范围内的长期链接，
在此之前**文件块是唯一可靠的交付形态**。

## 标准两步

### 第一步：对话框里先给 HTML

动画定稿后**立刻把 HTML 文件发到对话框**，让人能预览、能点下载——不要等文档做完再一起给。
用 agent 自己的文件发送能力（本环境是 `SendUserFile`，`display: 'render'` 可直接在侧栏打开）。

同时给一句使用说明：**点击画面暂停/继续、顶部 chips 切章节**——不说的话没人会去点。

### 第二步：生成飞书文档，把动画平铺进去

**先列出环境里实际可用的飞书工具再套流程，不要凭空假设工具名。**

文档结构（每个功能一份，顺序照抄）：

1. 标题：`<功能名> · 功能演示`
2. **callout 块**：一句话核心结论（取 manifest 的第一条 `claim`，不要另写）
3. 每一章一节：
   - heading2：`第 N 章 · <章节名>`
   - **GIF 图片块**（自动播放）
   - 2–3 行说明：直接取该章的 `claim` 与字幕文案，**不要另写一遍**，否则文档和动画会对不上
4. heading「关键数字」→ 表格：动画里出现过的所有数字（装载口 787mm、坡度 23°、可及半径 700mm…），
   与 `*-geo.ts` 的标定值一致
5. heading「可交互版」→ **HTML 文件块（附件，必须有）** + 一行说明：
   「下载后双击用浏览器打开，单文件离线可播；点画面暂停/继续，顶部 chips 切章节」。
   签名链接只能作为附件旁边的补充，不能拿它顶替附件
6. heading「演示说明（待确认）」→ 有序列表：manifest 的全部 `conceptualItems`
7. 页脚：`内部资料 · 请勿外传`

**多章动画一定要按章拆成多个 GIF**，每章一个插在自己的小节下面。拼成一条长 GIF 会同时踩两个坑：
体积超标加载慢，以及看的人不知道现在讲到哪一章。

## GIF 怎么产

```bash
python3 scripts/make-gif.py SceneA --out out/terrain-ch1.gif   # 默认已是 0.75 / every 5
```

**清晰度是硬约束，体积是软约束——搞反了就会被投诉「GIF 有点糊」（实测踩过）。**

飞书文档正文宽 700–900px，**Retina 屏按 2 倍渲染**，所以 GIF 横向像素要给到
显示宽度的 1.5–2 倍。`--scale 0.75`（→ 1440×810）是及格线，**不要为了省体积往下调**：

| scale | 尺寸 | 体积(13.6s) | 飞书里的观感 |
|---|---|---|---|
| 0.30 | 576×324 | 3.9MB | ❌ 顶栏小字糊成一团 |
| 0.38 | 730×410 | 5.4MB | ❌ 主字幕能读，整体发虚 |
| 0.55 | 1056×594 | 7.4MB | ⚠️ 勉强 |
| **0.75** | **1440×810** | **9.7MB** | ✅ **清晰，默认值** |

- 要省体积就**降帧率**（`--every 5` → 6fps）和**缩短单条时长**，不要降分辨率
- 脚本第二步用 ffmpeg `palettegen(stats_mode=diff)` + `paletteuse(dither=bayer)` 重做调色板，
  实测 11.8MB → 9.7MB，车身金属渐变肉眼无差别。**必须用 bayer 而不是误差扩散**——
  后者的噪点会毁掉 GIF 的帧间压缩，反而更大
- **1080p30 直接渲会被系统 OOM 杀掉**（实测 exit 137）：`--concurrency` 压到 2
- 单条控制在 **12MB 以内、时长 ≤15s**；飞书 `upload_all` 单次上限 20MB
- 画面越花（雪花、多地形切换）体积越大，同参数各章能差 1MB 以上，**每章都看一眼实际大小**
- 交付前**亲眼看一眼**（抽 3 帧裁到 1:1 放大）：主字幕、弹窗、HUD 读数都要能认出来

## OpenAPI 直连备查

环境只有裸 HTTP 时用，**执行前以 open.feishu.cn 官方文档为准**；需要 `docx` 与 `drive` 写权限：

- 建文档：`POST /open-apis/docx/v1/documents`
- 加块：`POST /open-apis/docx/v1/documents/{document_id}/blocks/{block_id}/children`
  （根节点的 block_id 即 document_id）
- 常用 block_type：text=2 · heading1=3 · ordered=13 · callout=19 · divider=22 · file=23 · image=27 · table=31
- 图片/文件三步走：① 先建**空的** image/file 块拿到 block_id → ②
  `POST /open-apis/drive/v1/medias/upload_all`（multipart：`parent_type=docx_image` 或 `docx_file`，
  `parent_node=` 该块 block_id）拿到 file_token → ③ PATCH 该块把 token 写回
- **GIF 必须走 image 块**才会自动播放；走 file 块就只是个附件卡片，点开才动

## 交付闭环

- 文档建好后把**文档链接**发回对话框，并列出文档里的块清单（哪几节是 GIF、哪个是附件）
- 有截图能力就截文档首屏确认 GIF 在正确位置且在播放；没有就明确说「未能预览，请打开确认」
- 动画后续有改动 → 重新导出 GIF → **更新原文档**（替换图片块），**不要另建新文档**，
  否则团队里会流传好几个版本
