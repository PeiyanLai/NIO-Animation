# 动画路由规则

## 两层判断

不要只按“功能名称”分类。先判断演示空间，再判断功能机制。

| 演示空间（scope） | 适用内容 | 主画面 |
|---|---|---|
| `vehicle-exterior` | 车灯、车门、充电口、尾门等 | 外观主视角 + 局部特写 |
| `cockpit` | 车机、NOMI、屏幕、方向盘交互 | 座舱 + HMI 覆盖层 |
| `vehicle-environment` | 地形识别、泊车、环境触发 | 车外环境 → 座舱 → 车外结果 |
| `vehicle-ecosystem` | 宠物硬件、外设、手机联动 | 外设/对象 → 车辆 → 自动结果 |
| `vehicle-system` | 预热、热管理、底盘控制等 | 车型概念示意 + 状态卡 + 多端页面 |
| `fleet-topology` | 组队、对讲、无网通信 | 地图、节点、链路与终端状态 |

`mechanism` 可多选：`user-action`、`automatic-detection`、`state-transition`、`device-pairing`、`data-sync`、`relay-network`、`exception-handling`。

## 输出形式

| 条件 | 输出形式 |
|---|---|
| 一条用户路径、状态不超过 3 个 | 单段线性演示 + 播放控制 |
| 自动触发并切换座舱/外观 | 3–5 章叙事动画 |
| 状态机、多端同步、不可用原因或冲突规则 | 主叙事动画 + 可点击章节/状态探索 |
| 多节点关系、网络桥接、不同终端能力 | 地图/拓扑动画 + 场景切换 |

## 分镜模板

### 环境触发

1. 建立环境与车辆位置。
2. 让环境变化抵达车辆，而不是让车辆无目的漂移。
3. 进入座舱显示系统判断或用户确认。
4. 回到外观展示可感知的结果。

### 外设自动化

1. 展示外设与对象的绑定。
2. 展示车辆识别到的条件。
3. 展示自动执行与清晰状态。
4. 展示退出条件及结果。

### 不可见系统

1. 用用户可理解的触发条件起场。
2. 用概念化部位表现处理过程。
3. 用状态栏、进度或设备同步展示过程。
4. 用用户价值收束，不逐条演示底层信号。

### 网络拓扑

1. 先演示正常连接。
2. 让断网节点变灰或断开，不用抽象文字替代。
3. 展示对讲机/有网车辆的桥接路径。
4. 用清晰的可达/不可达结果结束。

## 需求缺口处理

- 缺车型：追问车型；没有车型时只用中性概念车。
- 缺实体键位：显示“方向盘确认”等概念性交互提示，不绑定具体物理按钮。
- 缺正式 UI：创建与品牌视觉一致的概念状态卡，并在演示说明中列为待确认。
- 缺硬件外观：用中性硬件图标和命名，不臆造品牌硬件细节。
- 文档给出大量异常分支：主动画只走代表性 happy path；其余分支进入可点击状态探索。
