# 功能动画需求描述模版（详版 v2）

> 从 6 个成品动画逆向提炼。与简版（背景/用户/功能事实/叙事/约束/交付/验收
> 七段）的关系：**简版用于立项沟通，详版用于正式把需求交给 agent 制作**。
> 每节标注了【必填】或【可由 agent 提案 → 你确认】——PM 不需要全会写，
> 但提案确认过的内容返工算 agent 的，没写没确认的返工算需求的。

---

## 0. 元信息【必填】

| | |
|---|---|
| 功能名 / 提出人 / 优先级 | |
| 状态 | 量产功能 / **概念方案（全片挂「设计开发中」标注）** |
| 车型 | 点名车型写这里；不点名则由 agent 按素材库选 |

## 1. 功能定位与教育目标【必填】

- 一句话定位：这个功能是什么
- **看完动画，观众要会做什么 / 要相信什么**（1–3 条，这决定叙事重点）
- **全片最重要的一个知识点/卖点**（例：泊车 =「转角不等旋转、相等平移」；
  对讲 =「无网靠硬件不靠流量」；趴垫 =「人宠同排 + 收放零操作」）
- 叙事策略如有特殊要求写明（例：坡道用整整一章先演「不用会怎样」再给方案）

## 2. 舞台与视角【agent 提案 → 你确认】

每章用什么机位、为什么。确认时用两条判据把关：
- **主体位置拍得到**：宠物坐二排就不能选只拍前排的图
- **动作方向读得出**：椅背放倒/翻边立起是竖直运动 → 侧视；
  空间关系/轨迹/够得着 → 俯视。**逐章核对核心动作的方向**，不要全片一个机位套到底

## 3. 主体清单【必填核心列，约束列可 agent 补】

| 主体 | 呈现方式 | 位置/朝向/大小 | 关键约束 |
|---|---|---|---|
| 例:橘猫 | 真实照片剪纸 | 坐二排右侧,头朝车头 | 朝向连锁:绳锚点在反侧 |
| 例:固定开关 | **实车控件**(照片锚定) | 岛台储物开关 | **不虚构专用按键** |
| 例:第三方车 | 中性矢量 | 4700×1850,同尺换算 | 三维拉开差距,不影射车型 |

填写要点：
- 每个主体标明**实拍剪纸 / 实车控件 / 概念矢量**三者之一——概念的自动进第 7 节
- 位置写到「选图能选对」的粒度；朝向是产品语义不是构图（猫朝车头是需求）
- 涉宠物一律真实画像；生物的**姿态要与机位匹配**（俯视配趴卧/正面，侧视配侧姿），
  素材库没有对应姿态照片就在这里注明「需提供照片」

## 4. 章节详述【必填——这是整个模版的核心】

每章按这个格子写，**一章 = 5 拍左右的画面事件序列**（成品全部是这个节奏）：

```
第 N 章 · <标题>（预期时长 s）· 本章 claim:<一句话结论>
1. <起始画面:谁在哪,什么状态>
2. <事件/用户动作:谁做了什么>        ← 用户动作要明确标出（状态机跃迁点）
3. <机构/系统如何响应:什么动了,朝哪动>
4. <数值/标注出现:量出什么给观众看>
5. <本章结束状态 + 收尾字幕>
```

粒度自检：**每一拍都能回答「画面上此刻发生了什么」**。
「托盘翻出与椅背拼成狗床」合格；「展示托盘功能」不合格。
反面教训：简版文档里一句「座椅放倒铺平」，实现时连错三轮
（概念杆/放倒方向/托盘形态）——机构类动作要写清**转轴在哪侧、朝哪个方向动、
动到什么位置为止、和什么联动**。

## 5. 关键数值与几何主张【必填数值，画法可 agent 提案】

| 数值 | 出现在哪一章 | 来源 |
|---|---|---|
| 例:787mm | 第一/三章标尺 | 产品数据 |
| 例:绳长 260mm | 活动范围弧+断言 | 产品定义 |
| 例:26.0°C | 恒温显示 | **概念值(需求只说"稳定舒适")→注明** |

要点：
- 「方便/够得着/放得下/出不去」这类形容词**全部换成可量的数**;给不出就写
  「概念值,agent 定一个并标注待确认」
- **几何关系尽量画上画面**（sin23°=787/2000 三边全标出）——这是可信度来源
- 决定画面的尺寸必须给（坡长决定坡度;包高 vs 坐高决定头露不露得出来）

## 6. 状态机与交互逻辑【有状态就必填】

- 状态枚举 + 推进方向（例:free→placed→locked→released,严格单向）
- **每次跃迁由哪个用户动作触发**（不许自动跳变——观众会以为"它自己会锁"）
- **正交声明**：哪两组状态互不相干（敞篷开合 × 固定解锁）——不声明就可能
  被做成一个动作绑两件事

## 7. 概念件清单【必填】

逐条列出画面里**实车没有/还没定义**的东西（造型、UI、键位、收纳位置…）。
它们会出现在成品页的「演示说明（待确认）」里。这个清单同时是你的
**需求缺口清单**——每归零一条，离可实拍/可开发近一步。

## 8. 断言（声称 → 检查）【agent 起草 → 你确认】

动画声称什么，就检查什么。你只需确认清单覆盖了第 1 节的教育目标：

| 画面在说 | 必须检查 |
|---|---|
| 例:出不去 | 全时间轴绳长不被拉长 |
| 例:够不到 | 起跳最高点 < 装载口(够到了叙事就废) |
| 例:不碰邻车 | 车身与邻车间距 ≥10px 全时间轴 |

## 9. 交付物【必填,一般照抄】

- 交互 HTML（章节 chips + 点击暂停），按平台能力交付文件本体
- 右上角每章高清 GIF 一键下载 + 全部打包（≥1440×810）
- 需要实拍分镜表 / MP4 的在此点名（默认不产）

---

## 附:给模版使用者的三句话

1. **第 4 节写得越像分镜，返工越少**——六个成品每章都是 5 拍,这不是巧合,
   是「一章一个 claim」在时长上的自然长度;
2. 有概念图/参考图**一定附上**并逐要素指认（"蓝色三角=收纳态托盘"）——
   图不解释,agent 会按自己的理解读;
3. 首版出来后的反馈按老规矩:**一次一批、编号列点、指位置给参照物**,
   哪里不对+对的标准是什么,不用说怎么改。
